# Goal to Proof

**AI 에이전트가 올바른 일을 하고, 끝까지 마치며, 결과를 증명하게 합니다.**

[English](README.md) · [웹사이트](https://aiopshwang.github.io/goal-to-proof/) · [방법론](https://aiopshwang.github.io/goal-to-proof/methodology.html) · [검증](https://aiopshwang.github.io/goal-to-proof/benchmarks.html)

![Goal to Proof — 작업을 끝내고 결과를 증명하세요.](assets/social-card.svg)

Goal to Proof는 AI 에이전트를 위한 가벼운 완료 계약(closure contract)입니다. 승인된 비단순 작업을 그럴듯한 완료 보고가 아니라 **직접 관찰된 결과**까지 이어 줍니다.

에이전트에게 새로운 권한을 부여하거나 사용자의 목표를 대신 정하지 않으며, 단순 작업에 무거운 프로세스를 강요하지도 않습니다. 바꾸는 것은 단 하나, "완료"의 정의입니다. 범위 안의 각 요구사항에는 최신 상태에서 얻은 직접적이고 범위가 일치하는 증거가 있어야 합니다.

```bash
npx skills add aiopshwang/goal-to-proof
```

명령 하나로 표준 Agent Skills 패키지가 설치됩니다. Codex와 Claude Code 마켓플레이스 경로는 [설치](#설치)에서 다룹니다.

## 해결하려는 문제

에이전트는 실제 결과보다 한 단계 앞에서 멈추기 쉽습니다.

- 변경을 요청했는데 계획만 작성합니다.
- 개별 컴포넌트는 통과했지만 실제 통합 경로는 실행하지 않습니다.
- 파일은 만들었지만 대상 사용자가 실제로 쓸 수 있는지 확인하지 않습니다.
- `git push`는 성공했지만 공개 결과를 다시 읽어 보지 않습니다.
- 대리 지표 하나를 확인한 뒤 더 넓은 결과까지 검증했다고 표현합니다.

이런 경우에도 완료 보고는 그럴듯하게 읽힙니다 — 증거를 요구하기 전까지는요. 완료 계약이 없다면:

> "릴리스를 푸시했습니다."

Goal to Proof를 사용하면:

> "공개 원격 저장소에 릴리스 태그가 있고, 저장소 자격 증명 없이 릴리스 페이지를 읽을 수 있으며, 배포된 아카이브에 예상 스킬 파일이 들어 있음을 확인했습니다."

두 번째 보고는 그 관찰을 실제로 수행했을 때만 더 강합니다. 직접 증거가 없으면 대신 **검증됨**, **부분 검증됨**, **검증되지 않음**을 정확히 구분해 표현해야 합니다.

## 작동 방식: 완료 계약

실제 완료가 필요한 작업에서 네 가지를 분명히 합니다.

1. **Result(결과)** — 작업이 끝났을 때 무엇이 달라져야 하는가.
2. **Target(대상)** — 누가 또는 무엇이 그 결과를 사용하거나 관찰할 수 있어야 하는가.
3. **Proof(증거)** — 성공과 그럴듯한 실패를 구분하는 가장 직접적인 실용 관찰은 무엇인가.
4. **Boundaries(경계)** — 무엇이 승인되었고, 제외되었으며, 새 권한이 필요한가.

그 뒤 에이전트는 결과에 도달할 수 있는 가장 가벼운 워크플로를 선택하고, 의존 단계를 완료한 다음, 모든 완료 주장에 맞는 증거를 연결합니다. 통제권은 사용자에게 남고, 승인된 범위 안의 실행과 검증은 에이전트가 책임집니다.

| 사용자가 소유하는 것 | 승인된 범위에서 에이전트가 소유하는 것 |
| --- | --- |
| 목표, 가치, 권한, 위험 감수 수준, 중요한 선택 | 방법, 순서, 되돌릴 수 있는 구현 선택, 진단, 실행, 검증 |

## 무엇이 다른가

- **또 하나의 방법론이 아니라 완료 게이트입니다.** 계획, 설계, 디버깅, 조사, 구현 방법은 여전히 도메인 스킬의 몫입니다. Goal to Proof는 언제 작업이 "완료"로 인정되는지만 정의합니다.
- **주장과 같은 모양의 증거 규율.** 증거는 주장한 범위와 일치해야 하고 최신 상태에서 나와야 합니다. 편한 대리 검사가 요청된 결과를 대신할 수 없습니다.
- **공개된, 범위가 명확한 검증.** 저장소에 활성화·행동·하드 게이트 사례로 구성된 공개 평가 게이트와 기록된 결과가 [`evals/`](evals/)에 함께 들어 있으며, 그 기록이 뒷받침하는 것 이상을 주장하지 않습니다.

## 언제 사용하는가

의존 단계가 있거나 통합·배포·공개 경계를 넘는 작업, 계획·부분 결과물·고립된 컴포넌트·대리 검사에서 멈추기 쉬운 작업에 사용하세요.

예시는 다음과 같습니다.

- 사용자에게 보이는 기능을 구현하고 실제 경로를 실행하는 일
- 버그를 고친 뒤 원래 재현 경로와 회귀 항목을 확인하는 일
- 결과물을 공개하고 원격 상태를 다시 읽는 일
- 문서·시각 자료·교육 자료를 만들고 최종 렌더를 여는 일
- 중요한 사실을 1차 자료로 추적할 수 있어야 하는 조사
- 비단순 진단, 증거 기반 의사결정 메모, 실행 가능한 계획 자체가 요청 결과인 일
- 승인된 다단계 작업을 실제 대상 환경까지 완료하는 일

단순 질의응답, 번역·서식 변경, 열린 아이데이션, 직접 확인이 명백한 일상적 단일 수정, 대상 워크플로 실행 없이 답변만 요청하는 읽기 전용 작업에는 자동으로 적용하지 않습니다. 반대로 계획·진단·의사결정 문서 자체가 비단순 요청 결과라면 완료 계약의 대상이 될 수 있습니다.

## 호출

Codex에서 완료 행동을 명시적으로 요청할 수 있습니다.

```text
$goal-to-proof 이 승인된 변경을 실제 대상까지 완료하고 결과를 증명해 줘.
```

비단순 완료 작업과 설명이 일치하면 스킬이 자동으로 활성화될 수도 있습니다. 특히 조기 완료가 가장 큰 위험일 때는 명시적으로 호출하는 편이 좋습니다.

## 설계 원칙

- **결과가 산출물보다 우선:** 무언가를 생성했다고 자동으로 사용 가능한 결과가 되지는 않습니다.
- **주장과 같은 모양의 증거:** 편한 대리 지표가 아니라 주장한 범위를 검사합니다.
- **최신 상태의 증거:** 마지막 관련 변경 뒤에 다시 확인합니다.
- **가능하면 실제 경계에서 확인:** 통합, 사용자, 기기, 계정, 렌더, 원격 상태를 직접 확인합니다.
- **권한은 사용자에게 유지:** 승인 없이 공개, 배포, 지출, 정보 노출, 되돌리기 어려운 행동, 범위 확장을 하지 않습니다.
- **낮은 의식 비용:** 단순 작업은 단순하게 처리하고 완료를 지키는 데 필요할 때만 절차를 사용합니다.
- **한계를 정확히 표현:** 접근 권한이나 증거가 없으면 완료 주장의 범위를 줄입니다.

[제품 원칙](docs/product-principles.md)과 [방법론](https://aiopshwang.github.io/goal-to-proof/methodology.html)에서 자세히 읽을 수 있습니다.

## 검증과 주장 범위

이 프로젝트는 세 가지를 구분합니다.

1. **패키지 유효성:** 매니페스트와 스킬 구조가 각 검증기를 통과하는가.
2. **호스트 동작:** 특정 호스트의 실행 환경에서 탐색·설치·호출되는가.
3. **작업 결과:** 정의된 평가 사례에서 스킬을 사용한 에이전트가 더 정확히 완료하는가.

한 단계의 통과가 다음 단계를 증명하지는 않습니다. 평가 계약과 범위가 명확한 증거는 [벤치마크 및 검증](https://aiopshwang.github.io/goal-to-proof/benchmarks.html)에서 확인하세요. 보편적인 생산성 또는 성공률 개선을 주장하지 않습니다.

**첫 라이브 A/B에서 측정된 것** ([전체 기록](evals/results/2026-08-28-live-ab.md)). 같은 과제를 동일한 조건에서 두 번 — 스킬이 닿는 쪽과 닿지 않는 쪽으로 — 실행하고, 두 답변을 반대편 호스트의 블라인드 심판이 채점했습니다.

- Claude Code·`sonnet`에서 `B07` 픽스처, 암당 8회: 스킬을 쓴 쪽이 증거를 명시한 비율 8/8 (없는 쪽 5/8), 검증 범위를 정직하게 구분한 비율 8/8 (없는 쪽 4/8, 단측 Fisher p = 0.038).
- Codex·`gpt-5.6-sol`(높은 추론 강도)에서는 양쪽 모두 이미 거의 만점이었습니다. 이 사례들로는 그 기준선과의 차이를 검출할 수 없습니다.
- 스킬 이름을 언급하지 않는 프롬프트에서는 후보 23회 중 9회만 발동했고, 전부 한 사례였습니다. 이름을 대면 매번 발동합니다. **설치만으로 대부분의 작업에서 에이전트의 행동이 달라지지는 않습니다.**

셀당 3~8회는 작은 표본이며, 기록에는 **행동이 동일한 두 암 사이에서도 같은 크기의 격차**가 나타난 사례가 포함되어 있습니다. 위 수치를 인용하기 전에 기록을 먼저 읽으십시오.

## 기원과 개인정보 보호

초기 행동 모델은 과거의 실제 작업 세션을 집계 분석해 만들었습니다. 분석 대상은 의도 정렬, 범위 통제, 승인 경계 안의 자율 실행, 처음부터 끝까지의 검증, 지속 가능한 체크포인트, 증거 우선 보고처럼 반복해서 나타난 작업 방식입니다.

원문 대화는 이 저장소에 포함하지 않았습니다. 개인 이름, 비밀, 일회성 선호, 비공개 내용, 세션 전문, 비공개 코퍼스 메타데이터는 공개 스킬에서 제외했습니다. 원천 자료는 설계에 활용됐을 뿐 성능 벤치마크가 아닙니다.
